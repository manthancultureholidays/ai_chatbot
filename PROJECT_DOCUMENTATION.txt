PROJECT OVERVIEW
================================================================================

Project Name: AI Travel Chatbot (RAG-Based Q&A System)
Type: Full-Stack Web Application with RAG (Retrieval-Augmented Generation)
Architecture: Client-Server with LLM Integration
Purpose: Intelligent Q&A system for travel agent data analysis and insights

Key Capabilities:
- Natural language query processing
- Real-time streaming responses
- Data quality analysis and anomaly detection
- Login pattern analysis
- Company and agent information retrieval
- Multi-level search with fuzzy matching
- Caching for performance optimization

│  │   Routes     │→ │ Controllers  │→ │  Middleware  │      │
│  │   (api.js)   │  │ (query/stats)│  │ (validation) │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                      BUSINESS LOGIC LAYER                    │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │ Vector       │  │ Data         │  │ LLM          │      │
│  │ Service      │  │ Analyzer     │  │ Service      │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
│  ┌──────────────┐  ┌──────────────┐                        │
│  │ Cache        │  │ Answer       │                        │
│  │ Service      │  │ Extractor    │                        │
│  └──────────────┘  └──────────────┘                        │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                      DATA ACCESS LAYER                       │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │ Database     │  │ File System  │  │ External     │      │
│  │ Service      │  │ (JSON)       │  │ APIs (LLM)   │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                      INFRASTRUCTURE LAYER                    │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │ SQLite DB    │  │ Logger       │  │ Error        │      │
│  │ (agents.db)  │  │ (Winston)    │  │ Handler      │      │
│  └──────────────┘  └──────────────┘  └──────────────┘      │
└─────────────────────────────────────────────────────────────┘

Request Flow:
1. Client sends HTTP POST to /api/ask
2. Express routes to queryController
3. Validation middleware checks input
4. Controller checks dataAnalyzer for direct answers
5. If not found, vectorService performs search
6. Context retrieved and sent to llmService
7. LLM generates streaming response
8. Response streamed back to client
9. All actions logged via Winston
10. Errors caught by errorHandler middleware

2. VECTOR SERVICE (services/vectorService.js)
--------------------------------------------------------------------------------
Core search and retrieval engine using in-memory indexing.

Class Structure:
```javascript
class VectorService {
    constructor() {
        this.agentData = [];
        this.agentLoginData = [];
        this.initialized = false;
        // Indexes created in _buildIndexes()
    }
}
```

Indexes Created:
1. agentByEmail: Map<email, agent>
   - O(1) lookup by email address
   - Case-insensitive keys

2. agentByID: Map<agentID, agent>
   - O(1) lookup by agent ID
   - Case-insensitive keys

3. agentByName: Map<name, agent>
   - O(1) lookup by full name
   - Case-insensitive keys

4. agentByCompany: Map<company, [agents]>
   - O(1) lookup by company name
   - Returns array of all agents from company

5. agentByNationality: Map<nationality, [agents]>
   - O(1) lookup by nationality
   - Returns array of all agents from country

6. loginsByIdentifier: Map<identifier, [logins]>
   - O(1) lookup of login history
   - Works with email or agent ID

7. loginsByID: Map<loginID, login>
   - O(1) lookup by login record ID

8. searchIndex: Map<token, Set<agentIDs>>
   - Inverted index for token-based search
   - Tokens are 3+ character words

Key Methods:

init()
- Connects to cache and database
- Loads agent and login data
- Builds all indexes
- Sets initialized flag

search(query)
- Main search method
- Returns array of {id, content, score}
- Implements multi-strategy search

Search Strategy (in priority order):
1. Extract identifiers (emails, agent IDs, login IDs)
2. Direct lookup in indexes (O(1))
3. Company name matching (exact + fuzzy)
4. Nationality matching
5. Name matching (exact + fuzzy)
6. Token-based inverted index search
7. Return top results sorted by score

Fuzzy Matching:
- Algorithm: Levenshtein distance
- Threshold: 0.7 (70% similarity)
- Applied to: names, companies, tokens
- Handles typos and variations

_levenshtein(a, b)
- Calculates edit distance between strings
- Dynamic programming implementation
- Returns minimum edits needed

_fuzzyMatch(query, target, threshold)
- Wrapper around Levenshtein
- Normalizes distance to 0-1 score
- Returns true if above threshold

_buildAgentContent(agent)
- Formats agent data for LLM context
- Includes all relevant fields
- Merges login history
- Returns formatted string

Caching:
- All search results cached
- Cache key: "search:{query}"
- TTL: 3600 seconds (1 hour)
- Automatic invalidation

Performance:
- Index building: O(n) where n = total records
- Exact search: O(1) average case
- Fuzzy search: O(n*m) where m = string length
- Token search: O(k) where k = matching agents

3. LLM SERVICE (services/llmService.js)
--------------------------------------------------------------------------------
Manages LLM integration with fallback support.

Supported LLMs:
- Primary: Ollama (local deployment)
- Fallback: vLLM or remote Ollama

Configuration (via .env):
- OLLAMA_URL: Primary Ollama endpoint
- OLLAMA_MODEL: Model name (default: llama3.2:latest)
- FALLBACK_LLM_URL: Backup LLM endpoint
- FALLBACK_LLM_TYPE: Type (ollama/vllm)
- FALLBACK_MODEL: Fallback model name
- LLM_TIMEOUT: Request timeout (30000ms)
- LLM_MAX_RETRIES: Retry attempts (2)

Features:
- Streaming responses
- Automatic retry with exponential backoff
- Graceful fallback
- Error handling

Response Flow:
1. Try primary Ollama with streaming
2. On failure, retry with exponential backoff
3. If max retries exceeded, switch to fallback
4. If all fail, throw error

- LOG_LEVEL: Logging level (default: info)
- NODE_ENV: Environment (development/production)

Example .env file:
PORT=5000
OLLAMA_URL=http://localhost:11434/api/generate
OLLAMA_MODEL=llama3.2:latest
FALLBACK_LLM_URL=http://backup-server:8000/v1/completions
FALLBACK_LLM_TYPE=vllm
FALLBACK_MODEL=meta-llama/Llama-2-7b-chat-hf
LLM_TIMEOUT=30000
LLM_MAX_RETRIES=2
LOG_LEVEL=info
NODE_ENV=development

TROUBLESHOOTING
================================================================================

Common Issues:

1. Server won't start
   - Check port availability
   - Verify .env configuration
   - Check logs/error.log

2. LLM not responding
   - Verify Ollama is running
   - Check OLLAMA_URL
   - Test fallback configuration

3. No search results
   - Verify data files exist
   - Check database connection
   - Review vector service logs

4. Frontend can't connect
   - Verify backend is running
   - Check CORS configuration
   - Verify API_URL in frontend

5. Rate limit errors
   - Wait 15 minutes
   - Adjust rate limit settings
   - Check IP address

Debug Mode:
- Set LOG_LEVEL=debug in .env
- Check logs/combined.log
- Enable console logging
